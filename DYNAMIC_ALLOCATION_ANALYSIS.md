## 3. ESP-IDF API Calls (Internal Allocation)

These ESP32 SDK functions perform dynamic allocations internally (on the system heap or in specific driver pools).

- `esp_now_init()`: Allocates ESP-NOW driver control structures.
- `esp_now_add_peer()`: Allocates memory to store peer information in the driver table (limit of 20 on ESP32).
- `esp_now_del_peer()`: Frees the memory associated with the peer in the driver.
- `nvs_flash_init()`: Allocates cache buffers and control structures for NVS.
- `nvs_open()`: Allocates handles and buffers for NVS namespace operations.
- `nvs_set_blob()`: May allocate temporary buffers for flash writing.

## 4. Assessment and Risks

### Heap Fragmentation
The fragmentation risk in this component is **Moderate**.
- Most FreeRTOS allocations (tasks, queues, mutexes) are static after initialization, which is excellent for stability.
- The critical point identified is the use of `std::vector` in `PeerManager` and `EspNowManager`. Every time `get_all()` or `get_peers()` is called, a new memory block is allocated on the heap for the copy, and released shortly after. In systems with limited heap and many calls to these methods, this can lead to fragmentation.

### Recommendations (Optional)
1. **Avoid Vector Copies:** Change methods like `get_all()` to return constant references or use callbacks (iterators) to process peers without allocating new vectors.
2. **Replace `std::vector`:** Use `etl::vector` (Embedded Template Library) or a static array-based implementation with `MAX_PEERS` size, completely eliminating runtime allocations in `PeerManager`.
3. **FreeRTOS Static Allocation:** If the ESP-IDF version allows it, queues and tasks could use the `*_create_static` variants to ensure memory comes from pre-allocated buffers in the data segment, eliminating the risk of failure due to heap exhaustion after boot.
